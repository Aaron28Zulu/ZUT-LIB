# Architecture

## Layers

```
screens/ and widgets/      UI only. Reads AppState, calls service interfaces.
state/app_state.dart       Owns the signed-in session and exposes the services.
services/*.dart            Abstract interfaces (NFR-11). The only thing screens import.
services/mock/             Offline implementations used for the demo.
data/                      DataStore: in-memory tables, persisted to shared_preferences.
models/                    Plain immutable data classes with fromJson/toJson.
core/                      Clock, business rules, permissions, errors, theme, formatting.
```

Dependencies point downward only. A screen never touches `DataStore` or a `Mock*` class.

## Request flow

1. A screen calls a service method, for example `loans.request(resourceId)`.
2. The mock service checks the caller's permission through `MockContext.require`
   (FR-AUTH-08). A missing permission throws `PermissionDeniedException`.
3. It reads and writes tenant-scoped tables. `TenantTable.of(tenantId)` returns only
   that tenant's rows, so cross-tenant reads are impossible by construction (FR-TEN-02).
4. Business limits come from `core/rules.dart`, and time comes from `Clock.now()`.
5. `DataStore.commit()` notifies listeners and schedules a debounced save.
6. Failures surface as a sealed `AppException`; `runAction` in `widgets/actions.dart`
   turns them into snackbars or field errors.

## Data

- `assets/seed/*.json` is generated by `tools/generate_seed.py`. Dates in the seed are
  written relative to the anchor in `meta.json` and shifted to "now" on first load, so a
  fresh install always has current loans and sessions.
- Uploaded PDFs are stored base64 in local storage through `DataStore.saveFile`.
- Reset demo data clears storage and reloads the seed.

## Demo clock

`Clock.now()` returns real time plus an offset that the platform admin can move. All due
dates, collection expiries, overdue checks and reminders use it.
`runScheduledJobs` in `mock_services.dart` stands in for the scheduled cloud functions
and runs at start-up, when the app resumes and when the clock moves.

## Cloud mode (Firebase)

Offline stays the default build (SRS: offline prototype on seed data). Cloud mode is
opt-in at build time:

```bash
flutter run --dart-define=BACKEND=firebase
```

- `lib/core/backend.dart` reads the flag. `AppState.create` then starts Firebase and
  swaps `SharedPrefsStorage` for `FirestoreStorage`, so the services and screens are
  the same in both modes. The first cloud run uploads the seed.
- `FirestoreStorage` keeps each storage key as a document in `zutlib_kv`, split into
  200,000-character parts (Firestore's 1 MiB document limit). The whole demo state is
  one key, so two devices saving at once overwrite each other (last save wins), and a
  device only sees other devices' changes when it starts.
- Google sign-in goes through `IdentityProvider` (`FirebaseIdentityProvider`).
  `MockAuthService.signInWithGoogle` maps the Google email to an account in the chosen
  tenant, or creates a student account there. Without Google, the app signs in to
  Firebase anonymously so `firestore.rules` accepts it.
- Setup on a dev machine: `firebase login`, `flutterfire configure --project=<id>
  --platforms=android,web` (overwrites the placeholder `lib/firebase_options.dart`),
  `firebase deploy --only firestore:rules`, enable Google and Anonymous sign-in in the
  console, and add the debug keystore's SHA-1 to the Android app.

## Swapping mocks for Firebase

The SRS lists Firebase as the production backend (section 13). To move over:

1. Add `firebase_core`, `firebase_auth`, `cloud_firestore`, `firebase_storage` and
   `firebase_messaging`.
2. Write `FirebaseAuthService implements AuthService`, and the same for each interface.
   Role and tenant go into custom claims; Firestore security rules enforce tenant
   isolation, with tests on the Firebase emulator.
3. Move loan state changes and overdue checks into Cloud Functions, and replace
   `DeviceNotifier` with FCM.
4. Build a `ServiceBundle.firebase()` beside `ServiceBundle.mock()` and choose it in
   `AppState.create`. No screen code changes.

The existing service tests describe the expected behaviour and can be pointed at the new
implementations.
